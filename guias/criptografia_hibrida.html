Laboratorio L4 · ≈ 3 horas

TLS híbrido con OpenSSL

Montarás una PKI con ML-DSA, levantarás un servidor TLS 1.3 local y medirás, byte a byte y milisegundo a milisegundo, qué cuesta pasar de X25519 a X25519MLKEM768 y de ECDSA a ML-DSA. Después comprobarás qué negocian hoy servidores reales y reconstruirás en Python el secreto híbrido que entra en el key schedule.

Duración
≈ 3 h (+1 h opcional)
Nivel
Intermedio
Requisitos
Tema 2; shell de Linux o macOS
Actualizado
Septiembre 2026

L4.0Objetivos

  1. Usar las implementaciones nativas de ML-KEM y ML-DSA de OpenSSL 3.5+ desde la línea de órdenes.
  2. Generar una PKI de tres niveles (raíz → intermedia → hoja) con ECDSA P-256, ML-DSA-44 y ML-DSA-65, y validarla.
  3. Negociar TLS 1.3 con los grupos X25519, X25519MLKEM768 y MLKEM768 e identificar en la traza el key_share, el Certificate y el CertificateVerify.
  4. Medir el tamaño de cada mensaje y el rendimiento de conexiones completas, e interpretar los resultados con los conceptos del Tema 2 (ventana inicial de TCP, límite antiamplificación de QUIC).
  5. Comprobar qué grupo negocian hoy servidores públicos y explicar cuándo aparece un HelloRetryRequest.
  6. (Opcional) Reproducir con liboqs-python el key_share híbrido y el Handshake Secret de TLS 1.3.
Qué se ha verificado

Todas las órdenes y guiones de esta guía se ejecutaron el 24 de septiembre de 2026 en Linux x86-64 con OpenSSL 3.5.8 (25 de agosto de 2026) compilado desde las fuentes, y se repitieron las partes B–D con OpenSSL 4.0.2, con resultados idénticos salvo 1–2 bytes en el ClientHello. La parte F se ejecutó con Python 3.12.7, liboqs 0.16.0, liboqs-python 0.16.0.1 y cryptography 50.0.1. Las salidas que ves son reales; tus tiempos y algunos bytes (números de serie, nombres) variarán.

A2. La lista de grupos por defecto está en el código fuente (ssl/t1_lib.c). En 3.5.8 es:

"?*X25519MLKEM768 / ?*X25519:?secp256r1 / ?X448:?secp384r1:?secp521r1 / ?ffdhe2048:?ffdhe3072"

La sintaxis es nueva en 3.5 (página de manual SSL_CTX_set1_groups_list(3)): * marca los grupos para los que el cliente envía key_share especulativo; / separa tuplas de seguridad comparable, que un servidor OpenSSL usa para decidir si pide con HelloRetryRequest un grupo de una tupla preferida aunque el cliente haya enviado otro key_share aceptable (los clientes ignoran las fronteras de tupla); y ? ignora grupos desconocidos. La documentación advierte de que el ClientHello con X25519MLKEM768 puede no caber en un segmento TCP y romper cortafuegos defectuosos; anteponer ?X25519MLKEM768: sin * quita esa predicción. En OpenSSL 4.0.2 el primer bloque añade ?SecP256r1MLKEM768:?curveSM2MLKEM768.

Explica por qué 54 bytes bastan para reconstruir la clave privada completa (FIPS 204, ML-DSA.KeyGen_internal(ξ)) y qué ventaja tiene eso para guardar claves en un HSM o en una tarjeta.

L4.3Parte B · Una PKI con ML-DSA

El guion siguiente crea tres PKI de juguete, con raíz, intermedia y hoja para localhost, con el mismo algoritmo en toda la cadena. Guárdalo como pki.sh y ejecútalo en un directorio vacío.

#!/usr/bin/env bash
# Genera tres PKI de juguete (raíz -> intermedia -> hoja): ECDSA P-256, ML-DSA-44, ML-DSA-65
set -euo pipefail
mkdir -p pki && cd pki
cat > v3_ca.ext <<'X'
basicConstraints=critical,CA:TRUE,pathlen:0
keyUsage=critical,keyCertSign,cRLSign
subjectKeyIdentifier=hash
authorityKeyIdentifier=keyid
X
cat > v3_leaf.ext <<'X'
basicConstraints=critical,CA:FALSE
keyUsage=critical,digitalSignature
extendedKeyUsage=serverAuth
subjectAltName=DNS:localhost,IP:127.0.0.1
subjectKeyIdentifier=hash
authorityKeyIdentifier=keyid
X
keygen() {  # $1 = algoritmo, $2 = fichero
  case "$1" in
    EC)  openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out "$2" ;;
    *)   openssl genpkey -algorithm "$1" -out "$2" ;;
  esac
}
for ALG in EC ML-DSA-44 ML-DSA-65; do
  p=$(echo "$ALG" | tr 'A-Z' 'a-z' | tr -d '-')      # ec, mldsa44, mldsa65
  keygen "$ALG" "$p-root.key"
  openssl req -x509 -new -key "$p-root.key" -subj "/CN=Curso PQC Root $ALG" \
      -days 3650 -addext "keyUsage=critical,keyCertSign,cRLSign" -out "$p-root.crt"
  keygen "$ALG" "$p-int.key"
  openssl req -new -key "$p-int.key" -subj "/CN=Curso PQC Intermedia $ALG" -out "$p-int.csr"
  openssl x509 -req -in "$p-int.csr" -CA "$p-root.crt" -CAkey "$p-root.key" \
      -days 1825 -extfile v3_ca.ext -out "$p-int.crt"
  keygen "$ALG" "$p-leaf.key"
  openssl req -new -key "$p-leaf.key" -subj "/CN=localhost" -out "$p-leaf.csr"
  openssl x509 -req -in "$p-leaf.csr" -CA "$p-int.crt" -CAkey "$p-int.key" \
      -days 90 -extfile v3_leaf.ext -out "$p-leaf.crt"
  cat "$p-leaf.crt" "$p-int.crt" > "$p-chain.pem"          # lo que envía el servidor
  openssl verify -CAfile "$p-root.crt" -untrusted "$p-int.crt" "$p-leaf.crt"
done
$ chmod +x pki.sh && ./pki.sh

C3. Provoca un HelloRetryRequest. Reinicia el servidor solo con -groups secp256r1 y conecta con el cliente por defecto, que anuncia P-256 en supported_groups pero solo envía key_share para X25519MLKEM768 y X25519:

    ServerHello, Length=151

El primer «ServerHello» de 84 bytes es en realidad un HelloRetryRequest (RFC 8446 lo codifica como ServerHello con un valor fijo en random). El cliente repite el ClientHello, ahora con un key_share P-256, y ha escrito 1 941 bytes en lugar de ≈ 1 550. Repite con -groups MLKEM768 en el servidor: el cliente por defecto ni siquiera anuncia MLKEM768 y el handshake termina con la alerta handshake failure (40). Pregunta: ¿cuántos RTT cuesta el HRR y por qué un servidor bien configurado debería evitarlo?

L4.5Parte D · Medir tamaños y tiempos

D1. Tamaños. El guion medir.sh lanza un servidor por cada combinación de cadena y grupo, captura la traza del cliente y extrae la longitud de cada mensaje (sin las cabeceras de registro de 5 bytes):

#!/usr/bin/env bash
# Mide los mensajes del handshake TLS 1.3 para cada cadena y cada grupo.
set -uo pipefail
cd pki
printf "%-8s %-15s %6s %6s %6s %6s %8s %8s\n" cadena grupo CH SH Cert CV leidos escritos
for c in ec mldsa44 mldsa65; do
  for g in X25519 X25519MLKEM768 MLKEM768; do
    openssl s_server -accept 4433 -key $c-leaf.key -cert $c-leaf.crt \
        -cert_chain $c-int.crt -groups $g -www -quiet >/dev/null 2>&1 &
    srv=$!; sleep 0.5
    out=$(echo | openssl s_client -connect 127.0.0.1:4433 -CAfile $c-root.crt \
          -groups $g -trace 2>/dev/null)
    kill $srv; wait $srv 2>/dev/null
    len() { echo "$out" | grep -m1 -oE "$1, Length=[0-9]+" | grep -oE '[0-9]+$'; }
    rw=$(echo "$out" | grep -oE 'has read [0-9]+ bytes and written [0-9]+' | grep -oE '[0-9]+')
    printf "%-8s %-15s %6s %6s %6s %6s %8s %8s\n" $c $g "$(len ClientHello)" \
       "$(len ServerHello)" "$(len Certificate)" "$(len CertificateVerify)" $rw
  done
done

Cómo leerlo: el grupo solo cambia ClientHello y ServerHello (+1 176 y +1 088 bytes); la firma solo cambia Certificate y CertificateVerify. Los dos efectos son independientes y se suman. Las longitudes son las del cuerpo del mensaje: CertificateVerify = 2 (esquema) + 2 (longitud) + firma, es decir, 2 424 = 4 + 2 420 con ML-DSA-44; Certificate = 4 + Σ (3 + DER + 2) sobre los dos certificados, es decir, 8 116 = 4 + 4 071 + 4 041. La fila ec · X25519 se puede reconstruir entera: 127 (SH + registro) + 6 (ChangeCipherSpec) + 28 (EE) + 928 (Cert) + 101 (CV) + 74 (Finished) = 1 264.

D2. Tiempos. s_time abre conexiones nuevas durante un intervalo y mide el tiempo de CPU del cliente (verificación de la cadena y del CertificateVerify, encapsulado o DH). No acepta -groups, así que el guion fija el grupo con un openssl.cnf mínimo (directiva Groups):

#!/usr/bin/env bash
# Conexiones TLS 1.3 completas por segundo (s_time -new) para cada cadena y grupo.
set -uo pipefail
cd pki
for c in ec mldsa44 mldsa65; do
  for g in X25519 X25519MLKEM768 MLKEM768; do
    # configuración mínima de cliente que fija el grupo ofrecido
    cat > cli-$g.cnf <<X
openssl_conf = conf
[conf]
ssl_conf = ssl
[ssl]
system_default = def
[def]
Groups = $g
X
    openssl s_server -accept 4433 -key $c-leaf.key -cert $c-leaf.crt \
        -cert_chain $c-int.crt -groups $g -www -quiet >/dev/null 2>&1 &
    srv=$!; sleep 0.5
    r=$(OPENSSL_CONF=cli-$g.cnf openssl s_time -connect 127.0.0.1:4433 -new \
          -CAfile $c-root.crt -verify 2 -time 5 2>/dev/null | grep -m1 'connections/user sec')
    kill $srv; wait $srv 2>/dev/null
    printf "%-8s %-15s %s\n" $c $g "$r"
  done
done

En localhost no hay latencia de red, así que estas cifras solo miden CPU del cliente. El híbrido cuesta ≈ 13 % frente a X25519 (dos operaciones en vez de una) y el MLKEM768 puro es tan rápido como X25519. Verificar tres firmas ML-DSA-65 en vez de tres ECDSA reduce el ritmo ≈ 40 %. En una red real dominaría otro efecto: los viajes de ida y vuelta adicionales cuando el primer vuelo supera la ventana inicial de TCP (≈ 14 600 bytes), que en localhost (MTU de 65 536) no se ve.

L4.7Parte F (opcional) · El secreto híbrido en Python

Reproducimos con liboqs-python y cryptography los dos key_share de X25519MLKEM768 (RFC 10024) y el Handshake Secret de la ecuación (2.2) del Tema 2. El guion comprueba su HKDF-Expand-Label contra los vectores de RFC 8448. La teoría de los combinadores (por qué basta concatenar aquí y por qué un KEM híbrido genérico como X-Wing necesita más) está en el Tema 5; el ejemplo interactivo Intercambio híbrido lo muestra paso a paso en el navegador.

"""Intercambio híbrido X25519 + ML-KEM-768 al estilo X25519MLKEM768 (RFC 10024).

Reproduce los mensajes key_share y el secreto compartido que entra en el
key schedule de TLS 1.3. Requiere liboqs-python y cryptography.
"""
import hashlib, hmac, time
import oqs
from cryptography.hazmat.primitives.asymmetric.x25519 import (
    X25519PrivateKey, X25519PublicKey)
from cryptography.hazmat.primitives.serialization import Encoding, PublicFormat

RAW = dict(encoding=Encoding.Raw, format=PublicFormat.Raw)

def hkdf_extract(salt: bytes, ikm: bytes) -> bytes:
    return hmac.new(salt, ikm, hashlib.sha256).digest()

# --- Cliente: genera ambas claves efímeras (ClientHello.key_share) ---------
kem_c = oqs.KeyEncapsulation("ML-KEM-768")
ek = kem_c.generate_keypair()                    # clave de encapsulado, 1184 B
x_c = X25519PrivateKey.generate()
client_share = ek + x_c.public_key().public_bytes(**RAW)   # ML-KEM primero

# --- Servidor: encapsula y hace DH (ServerHello.key_share) -----------------
ek_rx, xpub_rx = client_share[:1184], client_share[1184:]
with oqs.KeyEncapsulation("ML-KEM-768") as kem_s:
    ct, ss_kem_s = kem_s.encap_secret(ek_rx)     # texto cifrado, 1088 B
x_s = X25519PrivateKey.generate()
ss_x_s = x_s.exchange(X25519PublicKey.from_public_bytes(xpub_rx))
server_share = ct + x_s.public_key().public_bytes(**RAW)
ss_server = ss_kem_s + ss_x_s                    # 32 + 32 = 64 B

# --- Cliente: desencapsula y completa el DH --------------------------------
ss_kem_c = kem_c.decap_secret(server_share[:1088])
ss_x_c = x_c.exchange(X25519PublicKey.from_public_bytes(server_share[1088:]))
ss_client = ss_kem_c + ss_x_c

assert ss_client == ss_server
print(f"client key_share : {len(client_share)} B")
print(f"server key_share : {len(server_share)} B")
print(f"shared secret    : {len(ss_client)} B = ML-KEM(32) || X25519(32)")

# (EC)DHE -> Handshake Secret, RFC 8446 §7.1 (SHA-256, sin PSK)
def hkdf_expand_label(secret: bytes, label: str, context: bytes, n: int) -> bytes:
    full = b"tls13 " + label.encode()
    info = n.to_bytes(2, "big") + bytes([len(full)]) + full + bytes([len(context)]) + context
    out, t, i = b"", b"", 1
    while len(out) < n:
        t = hmac.new(secret, t + info + bytes([i]), hashlib.sha256).digest()
        out, i = out + t, i + 1
    return out[:n]

zeros = bytes(32)
early_secret = hkdf_extract(zeros, zeros)
derived = hkdf_expand_label(early_secret, "derived", hashlib.sha256(b"").digest(), 32)
# Comprobación con los vectores de RFC 8448 (handshake 1-RTT sin PSK)
assert early_secret.hex().startswith("33ad0a1c607ec03b")
assert derived.hex().startswith("6f2615a108c702c5")
handshake_secret = hkdf_extract(derived, ss_client)   # IKM = ML-KEM || X25519
print("handshake_secret :", handshake_secret.hex()[:32], "...")

# Coste de cada operación (media de 2000 repeticiones, µs)
def bench(f, n=2000):
    t = time.perf_counter()
    for _ in range(n):
        f()
    return (time.perf_counter() - t) / n * 1e6

with oqs.KeyEncapsulation("ML-KEM-768") as k:
    pk = k.generate_keypair()
    c, _ = k.encap_secret(pk)
    print(f"ML-KEM-768 keygen {bench(k.generate_keypair):6.1f} µs | "
          f"encaps {bench(lambda: k.encap_secret(pk)):6.1f} µs | "
          f"decaps {bench(lambda: k.decap_secret(c)):6.1f} µs")
peer = X25519PrivateKey.generate().public_key()
print(f"X25519     keygen {bench(X25519PrivateKey.generate):6.1f} µs | "
      f"DH     {bench(lambda: x_c.exchange(peer)):6.1f} µs")

L4.10Problemas frecuentes

  • Error initializing ML-DSA-65 context (inner_evp_generic_fetch:unsupported) o group 'X25519MLKEM768' cannot be set: estás usando un OpenSSL anterior a 3.5 (salida real de OpenSSL 3.0.13). Revisa which openssl y LD_LIBRARY_PATH.
  • Can't open ".../ssl/openssl.cnf": falta make install_ssldirs (L4.1).
  • bind: Address already in use: queda un s_server vivo; pkill -f "s_server -accept 4433".
  • verify error:num=20:unable to get local issuer certificate: el -CAfile no corresponde a la cadena del servidor, o el servidor no envía la intermedia (-cert_chain).
  • s_time ignora tu grupo: la variable OPENSSL_CONF debe apuntar a un fichero que empiece por openssl_conf = …, como en tiempo.sh.
  • Wireshark no descifra: el fichero de claves debe ser el de esa conexión; cada ejecución de s_client genera secretos nuevos.
